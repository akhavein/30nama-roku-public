# Bounded API scheduling and transport

The SceneGraph controller now schedules `ApiTask` work through `ApiScheduler.brs`: at most two running API Tasks, sixteen pending Tasks, a 100 ms gap between initial starts, and a thirty-second pending deadline. Login/deep-link/playback reads have priority; equal-priority work is FIFO. Background prefetch has lowest priority. Page cancellation and session invalidation remove queued work as well as active work. Request IDs prevent old callbacks from freeing a newer slot. The timer stops when the pending queue empties.

The limits apply to `ApiTask` calls, including helper health/progress. Caption, preview and managed-session Tasks retain their existing independent bounds; this is not a global cap over every network operation. A retry retains its API slot and uses a minimum one-second delay. It does not re-enter the initial-start spacing scheduler.

`ApiPolicy.brs` permits transport retries only for catalog, search, detail, stream and next-prefetch reads on timeouts/native errors, HTTP 429 or 5xx. There are at most two attempts, each with the existing six-second read timeout. Numeric `Retry-After` values up to ten seconds are honored. Longer, malformed or HTTP-date values cause the request to finish without an automatic retry; they are never shortened into an earlier retry. Headers use `roUrlEvent.GetResponseHeadersArray`, which includes error-status headers, unlike `GetResponseHeaders` ([Roku reference](https://developer.roku.com/dev/docs/rourlevent)). Watchlist toggles, login approval, progress and unknown operations are not automatically replayed by transport.

Outgoing serialized bodies are limited to 16,384 characters. Before JSON parsing, responses are limited by operation: 8 KiB characters for helper health/progress; 32 KiB for login; 64 KiB for profile; 256 KiB for other operations; 1 MiB for search/stream/prefetch; 2 MiB for catalog/history. These are **parsing/retention ceilings**, not wire-byte ceilings: `roUrlTransfer` supplies a completed response string before the application can inspect it. True streaming download limits need a separately validated file/streaming implementation. No live response corpus was sampled; legitimate oversized responses fail explicitly and may require measured tuning.

HTTP status zero is no longer converted into HTTP 200. Oversized requests/responses, queue saturation/expiry, invalid JSON and transport errors produce explicit failure envelopes, without raw response text or credentials in logs. Existing controller messages and login retry limits handle those failures.

## Evidence

`tests/api-policy.brs` exercises classification, response boundaries and Retry-After. `tests/api-scheduler.brs` executes queue saturation, priority/FIFO, spacing, cancellation and stale completion behavior. `tests/api-task.brs` executes the actual Task controller with only native transfer/time primitives substituted, including successful delayed recovery, non-retried writes, oversized payloads, malformed JSON and zero-status rejection. These are simulator/controller tests, not proof of Roku networking or physical playback. `npm run package` additionally validates the full existing suite and shipping ZIP.
